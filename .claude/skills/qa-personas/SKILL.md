# 7人の意地悪なQA（テスト観点漏れ撲滅スキル）

> 出典の発想: 「Claude Code に『7人の意地悪なQA』を仕込んでテストケースの観点漏れを潰した」(Ayaka)。
> 本スキルはその型を、このreal-estateプロジェクト（iOS SwiftUI、Pythonのスクレイピングとenricher、
> Supabase移行、AI購入分析）に合わせて作り直したものである。

## いつ使うか

- 変更箇所のユニットテストやレグレッションテストを設計するとき（CLAUDE.mdの「実装中はこまめにユニットテストを書く」）。
- `code-reviewer` agentによるレビュー（CLAUDE.mdの「方針確定時と実装完了時の2回必須」）で、観点のチェックリストとして使うとき。
- パーサ、enricher、マイグレーション、iOSロジックのPRを出す前に、セルフレビューとして使うとき。

## 基本の姿勢

「動いているはず」を信用せず、意地悪なくらい疑ってかかる。各ペルソナは、最低1つの確認観点を残す。観点が思いつかないペルソナは、まだ疑い足りていない。

## 7人のQAペルソナ

| # | ペルソナ | このプロジェクトで疑う点（代表観点） | 主な対象 |
|---|---------|-----------------------------------|---------|
| P1 | 新人ユーザー | 説明を読まずに直感で操作する。誤タップ、空入力、連打、オフライン、電波断、初回起動（空データ）でiOS画面が崩れないか。和暦端末やロケールの違い（`DateFormatter` の `en_US_POSIX` 共有）で表示が崩れないか | iOS UI/状態 |
| P2 | ベテラン現場担当 | 大量データと高速操作。ウォッチリストや比較が大量件数でも動くか。フィルタの多用、連続スクロール、バックグラウンド復帰後の整合（`ios-performance-investigation` を参照） | iOS 性能/状態 |
| P3 | 悪意ある、または異常な入力をする人 | 境界値、不正値、想定外のフォーマット。価格0や欠損、全角数字、「-」、単位の揺れ、壊れたHTMLや改変されたHTML、文字コードの混在。botブロックを偽装したページ。パース例外を握り潰していないか | スクレイパー/パーサ |
| P4 | データ整合性の監査役 | 画面やログを信用せず、裏のDBを直接確認する。SupabaseとFirestoreのCRUD整合、dedupの取りこぼしと誤統合、delistingとgrace periodの整合、`upsert` の冪等性、versionとprompt_hashの正しさ | DB/dedup/enrich |
| P5 | 移行担当者 | 既存データの投入。Firebaseからの移行やマイグレーションでの欠損、異形式、件数の一致。マイグレーションの採番（既存最大番号に1を足した3桁。過去に025が衝突した）。新機能の作り方で移行を設計しない（要件は満たすが、既存仕様とずれるケースを取りこぼす） | 移行/migrations |
| P6 | 回帰デグレの番人 | 今まで動いていたものが壊れていないか。`tests/test_pipeline_smoke.py` のステージ間結線、単一ソースの同期（後述）、既存のユニットテスト、iOSの既存ロジック。CLAUDE.mdの「デグレ防止」の中心になる観点である | 全体/回帰 |
| P7 | 仕様懐疑者 | 実装が正しい仕様だとは考えない。単一ソースと実際の挙動を突き合わせる。対象は `ScrapingConfigMetadata.json` と `docs/SPECIFICATION.md`、`buyer_profile.json` と `purchase_strategy.md` と `prompts/<module>.md` と `docs/BUYER_PROFILE.md`、Supabaseの本番値。フェイルクローズの原則（取りこぼし側に倒す）が守られているかも確認する | 仕様/単一ソース |

### そのままプロンプトに貼れる版

```
あなたは「動いているはず」を信用しない7人のQAです。
各ペルソナの視点で、この変更を最低1つずつ壊しにいってください。
- P1 新人：誤タップ・空入力・連打・オフライン・初回起動・和暦/ロケール
- P2 ベテラン：大量データ・高速操作・バックグラウンド復帰後の整合
- P3 異常入力：価格0/欠損/全角数字・壊れたHTML・文字コード・bot偽装ページ・握り潰し例外
- P4 データ整合：画面でなく裏のDB(Supabase/Firestore)を直接確認。dedup・delisting・冪等upsert
- P5 移行：旧データ投入。欠損・件数一致・マイグレ採番。新機能の作り方で移行を設計しない
- P6 回帰：pipeline smoke・単一ソース同期・既存テスト・既存iOSロジックが壊れていないか
- P7 仕様懐疑：単一ソース(設定/戦略/仕様書/本番)と実挙動を突合。フェイルクローズが効くか
```

## 仕様の出どころで観点の軸を分ける（新機能と、移行・構造変更）

同じテストでも、仕様の出どころが違えば正解の基準も変わる。両者を混ぜると、出力にまとまりがなくなる。

| 観点 | 新機能・通常変更 | 移行・スクレイピング構造変更 |
|------|----------------|---------------------------|
| 仕様の出どころ | 課題やPRの要件と、該当するソースコード | 既存の挙動と既存データ、および単一ソース（設定、戦略、仕様書） |
| 正解の基準 | 要件を満たしていること | 既存仕様どおりに動き、取りこぼしがないこと |
| 中心になるペルソナ | P3 異常入力とP4 データ整合 | P5 移行とP6 回帰とP7 仕様懐疑 |
| 必須テスト | 純関数のユニットテスト | 同左に加えて `test_pipeline_smoke.py` と、件数と差分の検証 |

## 根拠のないケースや観点を出さない

テスト設計では、もっともらしいが根拠のないケースを量産しないことを最優先にする。

- 一次情報を引く。新機能なら課題やPRの番号と該当ソースの関数名を、移行や設定なら単一ソースの該当キー（`ScrapingConfigMetadata.json` のフィールド名など）を、観点の根拠として明示する。独自に採番した仕様や、推測した仕様を作らない。
- 確認できていないことは「未確認」と書く。コードやDBで裏を取れていない観点は、「要確認（未実施）」として残し、断定しない。分からないことを分からないと書くのが、もっとも誤りを減らす。
- やらないことを先に宣言する。たとえば「このレビューは指摘のみで修正はしない」「裏を取れない箇所は埋めない」と書いてから進める。AIが範囲を越えたり、事実をでっち上げたりするのを抑えられる。

## 出力の型（テスト観点を残すとき）

テスト設計の成果物（テスト観点表、PR説明のテスト節）には、最低限次の項目を残す。

- どのペルソナの視点か（P1からP7）と、疑った点。
- 根拠となる一次情報。課題やPRの番号、単一ソースの該当キー、ソースの関数名のどれか。
- 期待結果。特にP4では、裏のテーブルとカラムに正しい値が入るところまで書く。
- 回帰の対象か（YESかNO）。P6の観点である。変更で壊れる可能性がある周辺（pipeline smoke、単一ソースの同期）を明記する。
- 品質特性（ISO/IEC 25010、2023年版の9特性）での偏りの確認。機能適切性、性能効率性、互換性、使用性、信頼性、セキュリティ、保守性、移植性、安全性の9つである。

## このスキルとCLAUDE.mdの対応

- 「デグレ防止」と「レグレッションテスト必須」には、P6の回帰デグレの番人を毎回通す。
- 「設定の単一ソース」と「買い手コンテキストの正準ソース」には、P7の仕様懐疑者で突き合わせる。
- 「フェイルクローズ（取りこぼし側に倒す）」と「パース0件の終端とブロックの区別」には、P3とP7を当てる。
- 「`code-reviewer` agentを2回必須」には、このペルソナ表をレビューのチェックリストとして使う。
